# 競馬AI 三連複EVシステム 仕様書 v1.1

## 1. 目的

日本中央競馬を対象に、三連複で期待値の高い買い目を抽出するAIシステムを作る。

このシステムは、単なる「予想AI」ではなく、**市場オッズに対して割安な三連複を見つけるEV判定システム** とする。

基本思想は以下。

```text
買うべき馬券 = 当たりそうな馬券
ではなく
買うべき馬券 = 推定的中確率に対してオッズが高い馬券
```

---

## 2. 前提

```text
対象競馬：JRA中央競馬
対象馬券：三連複
実行環境：Mac
主な開発言語：Python
初期データ：Kaggleの2021年以前データ
2022年以降：自前スクレイピングで補完
自動投票：初期対象外
```

---

## 3. データ方針

### 3.1 基本方針

Kaggleデータは、2021年以前の初期データとして使う。

2022年以降のデータは、Kaggleの構造を参考にしながら、netkeiba等から自前で収集する。

最終的には、取得元に関係なく、同じ形式で扱えるようにする。

```text
Kaggleデータ
+
自前収集データ
+
JRA公式確認データ

↓

共通データ形式

↓

特徴量生成・学習・バックテスト
```

---

## 4. データ管理方針

今回の仕様では、データを以下の3層に分ける。

```text
raw層
standard層
feature層
```

ここが一番重要。

**取得や保存を後回しにするのではなく、モデル投入を段階的にする。**

---

# 5. raw層

## 5.1 目的

raw層は、取得したデータをできるだけ元に近い形で保存する場所。

ここでは、取れる情報はなるべく保存する。

```text
目的：あとで再取得しなくて済むようにする
```

## 5.2 保存対象

最初から可能な範囲で保存する。

```text
・レース結果ページ
・出馬表ページ
・オッズページ
・払戻ページ
・馬プロフィールページ
・血統ページ
・ラップ情報
・通過順
・馬場情報
```

raw層では、綺麗な形に整える必要はない。
HTML、CSV、JSON、Parquetなど、取得元に近い形で保存する。

## 5.3 方針

```text
取得：広め
保存：広め
整形：まだ最低限
モデル利用：まだしない
```

---

# 6. standard層

## 6.1 目的

standard層は、Kaggle由来データと自前収集データを同じ形にそろえる場所。

ここでは、まず三連複EV検証に必要なデータから整える。

## 6.2 最初に作る標準データ

```text
・レース情報
・出走馬情報
・レース結果
・人気
・単勝オッズ
・三連複オッズ
・払戻
```

これは最優先。

理由は、これがないと以下ができないから。

```text
・3着内の教師データを作れない
・三連複の的中判定ができない
・EVを計算できない
・回収率を検証できない
・バックテストできない
```

## 6.3 早期にstandard化したいデータ

```text
・馬体重
・馬体重増減
・斤量
・騎手
・調教師
・上がり3F
・通過順
・馬場状態
・天気
・距離
・競馬場
・芝ダート
・枠番
・馬番
```

これはモデル精度に関わるので、早めに整える。

## 6.4 後からstandard化するデータ

```text
・血統
・ラップ詳細
・調教
・厩舎コメント
・馬場含水率
・クッション値
・直前オッズ推移
```

これは取得できるならrawに保存しておく。
ただし、最初のモデルや最初のバックテストでは使わない。

---

# 7. feature層

## 7.1 目的

feature層は、モデルに入れるための特徴量を作る場所。

rawやstandardに保存してあるデータを、モデルが使える形に変換する。

## 7.2 最初に使う特徴量

最初のモデルでは、複雑な特徴量は使いすぎない。

```text
・競馬場
・距離
・芝ダート
・馬場状態
・頭数
・枠番
・馬番
・斤量
・騎手
・調教師
・人気
・単勝オッズ
・近走成績
・上がり3F
・通過順
```

まずはこれでベースラインを作る。

## 7.3 後から追加する特徴量

```text
・血統適性
・ラップ適性
・馬場含水率
・クッション値
・直前オッズ推移
・調教評価
・厩舎コメント解析
```

これらは、ベースライン完成後に追加する。
理由は、取得・整形・検証コストが高く、最初から入れると開発が重くなるため。

# 9. システム全体構成

```text
データ取得
  ↓
raw保存
  ↓
standard変換
  ↓
feature作成
  ↓
3着内確率モデル
  ↓
三連複組み合わせ生成
  ↓
EV計算
  ↓
買い目候補出力
  ↓
結果検証
```

---

# 10. モデル方針

モデルは3段階に分ける。

## Model A：3着内確率モデル

各馬が3着以内に入る確率を出す。

```text
p_top3 = その馬が3着以内に入る確率
```

最初はLightGBMなどの表形式データ向けモデルで作る。

## Model B：割安馬判定

AI評価と市場評価のズレを見る。

```text
AI評価は高い
しかし市場人気は低い
```

こういう馬を三連複候補に入れる。

## Model C：三連複EV判定

候補馬から三連複の組み合わせを作り、それぞれの期待値を計算する。

```text
EV = 推定的中確率 × 三連複オッズ
```

---

# 11. 買い目生成方針

```text
1. 各馬の3着内確率を出す
2. 3着内確率が高い馬を候補にする
3. 割安と判断された馬を候補に加える
4. 候補馬から三連複を生成する
5. 各買い目のEVを計算する
6. EVが高い買い目だけ残す
7. 点数上限をかける
8. 期待値がないレースは見送る
```

避ける買い方。

```text
・AI上位5頭BOX
・全レース購入
・人気馬だけの低配当三連複
・点数を増やして的中率を取りに行く買い方
```

# 12. バックテスト方針

バックテストでは、以下を見る。

```text
・回収率
・的中率
・総投資額
・総払戻額
・純利益
・最大ドローダウン
・月別成績
・オッズ帯別成績
・EV帯別成績
・レース条件別成績
```

検証は時系列で行う。

```text
過去データで学習
↓
別期間で検証
↓
直近期間でテスト
```

最初の大きな目標はこれ。

```text
2021年以前：Kaggle
2022年以降：自前収集

この2つを結合して、連続したバックテストができる状態にする
```

# 13. スクレイピング方針

スクレイピングは、データ基盤を作るための手段として使う。

方針は以下。

```text
・取得したHTMLは保存する
・同じページを何度も取りに行かない
・取得処理と解析処理を分ける
・大量並列取得はしない
・取得データを外部公開しない
・アクセス制限回避を前提にしない
```

処理は以下のように分ける。

```text
fetch：ページを取得して保存する
parse：保存済みHTMLから情報を抜き出す
normalize：共通形式に変換する
feature：モデル用特徴量を作る
```

# 14. 開発フェーズ

## Phase 1：Kaggleデータ理解

```text
・Kaggleデータを読む
・列の意味を確認する
・race_id / horse_id を確認する
・欠損や表記揺れを確認する
・必要なデータ単位を整理する
```

## Phase 2：raw保存・standard変換の設計

```text
・raw保存ルールを決める
・standard層の最低限テーブルを決める
・Kaggleデータをstandard形式へ変換する
```

## Phase 3：2022年以降データ収集

```text
・対象レース一覧を作る
・必要ページを取得してraw保存する
・保存済みHTMLから必要情報を抽出する
・standard形式に変換する
・Kaggle期間と結合する
```

## Phase 4：ベースラインモデル

```text
・3着内確率モデルを作る
・人気順ベースラインと比較する
・確率の妥当性を見る
・簡易的な三連複EV判定を作る
```

## Phase 5：三連複バックテスト

```text
・三連複の組み合わせを作る
・EV順に買い目を並べる
・買い目点数を制限する
・回収率とドローダウンを見る
```

## Phase 6：拡張特徴量の追加

```text
・血統を追加する
・ラップを追加する
・馬場詳細を追加する
・直前オッズログを追加する
・追加前後で成績を比較する
```

## Phase 7：当週運用

```text
・当週出馬表を取り込む
・当週オッズを反映する
・買い目候補を出す
・レース後に結果を保存する
・成績を更新する
```

# 15. ベスト案

最初の完成目標はこれ。

```text
Kaggleデータ
+
2022年以降の自前収集データ
+
共通standard形式
+
3着内確率モデル
+

```

この段階では、血統・ラップ・調教コメントまで無理に使わない。

ただし、取得できるものはrawとして保存しておく。
使うのを後回しにするだけ。

---

# 16. 代替案

三連複モデルに入る前に、3着内確率モデルだけを先に検証する案もある。

```text
Phase A：馬ごとの3着内確率を作る
Phase B：複勝・ワイド的に確率の妥当性を見る
Phase C：三連複の組み合わせ評価に進む
Phase D：EVフィルターを入れる
```

この方が、問題の切り分けがしやすい。

```text
3着内確率が悪いのか
組み合わせ確率が悪いのか
オッズ評価が悪いのか
買い目制御が悪いのか
```

を分けて見られる。

# 17. 注意点

この仕様で一番重要なのは、**取得・保存・利用を分けること**。

以前の「後回し」という表現は使わない。
正しくは以下。

```text
取得・raw保存：
取れるなら広めに保存する

standard化：
まず三連複EV検証に必要なものから整える

feature化：
最初はシンプルに作る

モデル投入：
効果検証しながら段階的に増やす
```

つまり、

```text
血統やラップを取らない
```

ではない。

正しくは、

```text
血統やラップは取れるなら保存する。
ただし最初のモデルには入れない。
```

という方針。

# 18. 最終まとめ

本システムは、Mac環境で動く日本中央競馬向けの三連複EV判定システムである。

```text
Kaggleの2021年以前データを初期土台にする。

2022年以降は自前でデータを収集する。

取得データはrawとして広めに保存する。

Kaggle由来データと自前収集データをstandard形式に統一する。

feature層では、まず最小構成で3着内確率モデルを作る。

三連複の組み合わせごとにEVを計算する。

期待値がある買い目だけを候補として出す。

血統・ラップ・馬場詳細・直前オッズ推移などは、保存できるものは保存し、モデルへの投入は段階的に行う。
```

この仕様の中心は、**データは広く保存し、モデル利用は狭く始める** こと。
